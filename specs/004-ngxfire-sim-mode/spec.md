# Feature Specification: ht-quick-ngxfire Simulation Mode

**Feature Branch**: `004-ngxfire-sim-mode`
**Created**: 2026-05-09
**Status**: Draft
**Input**: User description: "for the ht-quick-ngxfire I want to add a simulation mode where if they don't provide the firebase config json it defaults to that for all the firebase services"

## Clarifications

### Session 2026-05-09

- Q: How should the library handle a `firebaseOptions` that is partially populated — present, but missing the fields a particular enabled service needs to initialize? → A: Evaluate per-service. The library cross-references each enabled-service flag in `FirebaseConfig` (`firestore`, `database`, `functions`, `storage`, plus auth) against the `firebaseOptions` fields required to initialize that specific service. Where required fields are missing, that service simulates in dev and throws in prod. Other services on the same `FirebaseConfig` whose required fields *are* present continue to initialize against real Firebase. Result: a single app can run with some services real and others simulated.
- Q: Which `firebaseOptions` fields count as "required" for each service when the per-service activation decision runs? → A: Per-SDK minimum. The required-field map is: Auth → `apiKey` + `authDomain`; Firestore → `apiKey` + `projectId`; Realtime Database → `apiKey` + `databaseURL`; Functions → `apiKey` + `projectId`; Storage → `apiKey` + `storageBucket`. Because every service depends on `apiKey` (and Firestore/Functions/Auth-via-projectId on `projectId`), a missing `apiKey` causes every enabled service to simulate. This matches the minimum each Firebase SDK actually needs at init, so the simulator activates exactly when real init would have failed.
- Q: How is "production build" detected for the safety check, and can consumers override it (for tests, Storybook, e2e)? → A: Tri-state policy on `FirebaseConfig`. Add a `simulation: 'auto' \| 'force' \| 'forbid'` field (default `'auto'`). `'auto'` follows the framework's dev/prod signal — Angular's `isDevMode()` — so the default behavior is "simulate in dev, throw in prod" exactly as FR-005 originally described. `'force'` allows simulation regardless of build mode (tests, Storybook, e2e harnesses, demo deployments). `'forbid'` always throws on any missing required field regardless of build mode (paranoid consumers asserting real Firebase only). One config field; no extra injection token; the boolean working-name `simulation: true` from earlier drafts is replaced by `simulation: 'force'`.
- Q: Does the simulated Firestore emulate optimistic-concurrency contention for `runTransaction`, or run callbacks atomically without conflict? → A: Atomic single-pass with a documented limitation. The simulator runs the transaction callback exactly once against a consistent in-memory snapshot, then commits all writes atomically — no version tracking, no retries, no conflict synthesis. The limitation MUST be (a) called out in the spec/docs as a known gap between simulator and real Firestore, and (b) surfaced via a one-time runtime warning the first time `runTransaction` (or batch + read patterns) is committed in a session, telling the developer to validate transaction-using code against real Firestore or the Emulator Suite.
- Q: Does `<ht-login>` paint a visible "Simulation mode" affordance when auth is simulated, or stay visually identical to its real-Firebase rendering? → A: Default-on, suppressible badge. When the auth service is running simulated, `<ht-login>` MUST render a small accessible "Simulation mode" badge inside the component by default. Consumers MAY suppress it with an input (working name `[showSimulationBadge]="false"`) when they want a polished demo. The badge MUST meet the same WCAG 2.1 AA baseline the rest of the component meets (FR-AUTH-14) and MUST be styleable via a CSS custom property in the existing `--ht-login-*` token family.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Prototype an App Without a Firebase Project (Priority: P1)

A consuming app developer wants to evaluate `ht-quick-ngxfire`, build a demo, or prototype a feature without first creating a Firebase project, registering an app, copying the web config, or hooking up authentication providers in the Firebase console. They install the library, call `provideHtQuickNgxFire(...)` *without* supplying `firebaseOptions`, and the library transparently runs every Firebase-backed surface (Auth, Firestore, Storage, Realtime Database, Functions) against a built-in in-memory simulator.

**Why this priority**: This is the entire feature. Removing the Firebase setup gate is the value proposition — every other story is a refinement. If only this story ships, the library still becomes radically easier to try and to demo.

**Independent Test**: Bootstrap a fresh Angular app, register `provideHtQuickNgxFire({ authOptions: { email: true }, firestore: true, storage: true, database: true, functions: true })` with **no** `firebaseOptions` value, drop `<ht-login>` into a page, write a document via `HtFirestoreService`, and read it back — all without any Firebase project, network access, or environment variables.

**Acceptance Scenarios**:

1. **Given** a consumer calls `provideHtQuickNgxFire` with `firebaseOptions` omitted, undefined, or an empty object, **When** the application bootstraps, **Then** the library MUST activate simulation mode for every enabled service in `FirebaseConfig` and MUST NOT attempt any network call to Firebase.
2. **Given** simulation mode is active, **When** a user signs in via `<ht-login>` using any enabled provider (email/password or SSO), **Then** the call MUST succeed and produce a deterministic simulated `User` whose `uid`, `email`, and `displayName` are surfaced through `HtAuthService.user$` and `HtAuthService.currentUser`.
3. **Given** simulation mode is active, **When** a consumer calls any `HtFirestoreService` method (CRUD, queries, transactions, batch writes), **Then** the operation MUST complete against an in-memory store and MUST return results with the same shape as the real Firestore service.
4. **Given** simulation mode is active, **When** a consumer uploads a file via `HtStorageService`, **Then** the upload MUST complete with progress events emitted, the file MUST be retrievable by path or download URL within the same session, and metadata operations MUST work.
5. **Given** a consumer supplies a populated, valid-looking `firebaseOptions` that satisfies every enabled service's required fields, **When** the application bootstraps, **Then** the library MUST behave exactly as it does today (no simulation activation, no behavioral change).
6. **Given** a consumer enables `firestore: true` and `storage: true` in `FirebaseConfig` but supplies a `firebaseOptions` that contains the fields required by Storage and is missing the fields required by Firestore, **When** the application bootstraps in development mode, **Then** Storage MUST initialize against real Firebase, Firestore MUST activate its simulator, and the startup warning MUST identify Firestore (not Storage) as the simulated service.

### User Story 2 - Stay Safe Across Dev and Production (Priority: P2)

The same developer who prototypes locally eventually deploys. They must not silently ship a build where simulation mode is masking a missing Firebase config, because the production app would appear to "work" while persisting nothing and authenticating no one. The library treats simulation mode as a development-only default and refuses to silently activate it in a production build unless the consumer has explicitly opted in.

**Why this priority**: Without this guard, P1 is a footgun. The cost of accidentally shipping a simulated production app (lost data, fake auth) is high enough to justify a hard stop, but the protection is mechanical and can be added once P1 is stable.

**Independent Test**: Build the consumer app twice from the same source — once with Angular dev mode (`isDevMode() === true`) and once as a production build — both with `firebaseOptions` omitted. The dev build MUST start in simulation mode; the production build MUST fail fast at bootstrap with a clear error explaining that simulation mode requires explicit opt-in.

**Acceptance Scenarios**:

1. **Given** `firebaseOptions` is missing AND the Angular runtime reports development mode AND `simulation` is `'auto'` (default), **When** the application bootstraps, **Then** simulation mode MUST activate and the library MUST emit exactly one prominent console warning that lists every service running simulated (and, in hybrid configurations, every service running real).
2. **Given** any service enabled in `FirebaseConfig` lacks the `firebaseOptions` fields it needs to initialize AND the Angular runtime reports production mode AND `simulation` is `'auto'` (default), **When** the application bootstraps, **Then** the library MUST throw a `HtQuickNgxFireError` whose message names *each* under-configured service, lists the specific `firebaseOptions` fields each is missing, and explains the `simulation: 'force'` opt-in.
3. **Given** any required `firebaseOptions` field is missing AND the consumer has set `simulation: 'force'` on `FirebaseConfig`, **When** the application bootstraps in either dev or production mode, **Then** the affected services MUST simulate without throwing, and the warning from scenario 1 MUST still be emitted.
4. **Given** the consumer has set `simulation: 'forbid'` AND any enabled service is missing a required `firebaseOptions` field, **When** the application bootstraps in either dev or production mode, **Then** the library MUST throw `HtQuickNgxFireError` exactly as it would in the production-default case — `'forbid'` makes the prod check apply universally.
5. **Given** at least one service is running simulated, **When** a consumer reads the per-service simulation status map exposed by FR-007, **Then** the map MUST report each service's actual mode (`real` | `simulated` | `disabled`) before the first auth call resolves, so the consumer can render their own "demo mode" affordances or branch behavior at runtime.

### User Story 3 - Deterministic, Inspectable Simulated State (Priority: P3)

A developer demoing the library to a stakeholder wants the simulator to feel like a real backend during the demo: signing in twice produces the same user; documents written in one component appear in another; uploaded files render via a URL the browser can fetch; refreshing the page returns to a clean slate so the next demo starts fresh.

**Why this priority**: This is the difference between "the simulator technically works" and "the simulator is pleasant to use." It only matters once P1 is shipping and developers are actually demoing with it.

**Independent Test**: Sign in as `demo@example.com` from the login form, write a document under collection `notes`, navigate to a different route that lists `notes`, confirm the document appears with the same shape as if Firestore were live. Refresh the page; confirm the user is signed out and the `notes` collection is empty.

**Acceptance Scenarios**:

1. **Given** simulation mode is active, **When** the same email signs in twice in one session, **Then** both sign-ins MUST produce the same `uid` (deterministic per-email mapping within a session).
2. **Given** simulation mode is active, **When** any tab reloads the page, **Then** simulated auth state, Firestore data, Storage files, Realtime Database trees, and Functions stubs MUST reset to empty initial state.
3. **Given** simulation mode is active and a file has been uploaded via `HtStorageService`, **When** any component requests its download URL, **Then** the URL MUST be resolvable by the browser within the same page session (e.g., a blob/object URL).
4. **Given** simulation mode is active and a guard such as `htRoleGuard` is in use, **When** the simulated user has no assigned role, **Then** the guard MUST behave consistently with how it would behave against an empty real Firestore (i.e., deny access), so guard-protected demos remain testable.

### Edge Cases

- **Partially-supplied config (per-service)**: `firebaseOptions` is present but missing one or more fields required by an enabled service. The library MUST evaluate this **per service**: any enabled service whose required fields are present MUST initialize against real Firebase; any enabled service whose required fields are missing MUST simulate (in dev) or trigger the production-mode error (in prod). The library MUST NOT defer this decision to `@angular/fire`'s own initialization error — the per-service decision happens at `provideHtQuickNgxFire` evaluation time so the error message can be specific.
- **Hybrid real + simulated within one app**: A single application MAY end up running some services real (e.g., Storage with `storageBucket` set) and others simulated (e.g., Firestore with `projectId` missing) in the same session. The simulator and real-Firebase-backed services MUST coexist without one corrupting the other (e.g., real `HtAuthService` user state MUST NOT pollute the simulated Firestore role records and vice versa).
- **Mixed enablement**: Consumer enables `firestore: true` but `storage: false` while running in simulation. The library MUST activate the simulator only for services the consumer enabled — disabled services MUST remain absent from the injector exactly as today.
- **Per-call provider override (`signInWithProvider`)**: Simulated SSO sign-in MUST succeed regardless of which `providerId` is passed, but the resulting simulated user's `providerData[0].providerId` MUST reflect the requested provider so consumers can branch on it.
- **Concurrent sign-in attempts**: The login component's existing prevention (FR-AUTH-16) MUST continue to work — simulation MUST resolve the auth promise on the next microtask, not synchronously, so the loading state is observable.
- **`HtAuthAdminService` and `HtAuthUserSyncService`**: These services touch Firestore for role/profile data. They MUST work end-to-end against the in-memory Firestore so that role-gated demos behave realistically.
- **Real-time listeners (Firestore, RTDB)**: Snapshot subscriptions opened against the simulator MUST emit on subsequent writes from any other call site within the same app, so live-binding UIs update during a demo.
- **Existing tests**: The current test suite is written against `@angular/fire` and must continue to pass. Simulation mode MUST be off by default in the library's own test environment unless a test explicitly opts in.
- **Re-invocation of `provideHtQuickNgxFire`**: A consumer MAY call `provideHtQuickNgxFire(...)` more than once in the same app (e.g., via a feature module that re-provides it, or two parallel Angular apps in one page). The activation decision MUST be re-computed on each call, but the FR-004 dedup ensures only unique decisions emit a warning. If two calls produce conflicting per-service modes for the same service (e.g., one says `'real'` for Firestore, another says `'simulated'`), the second call's decision wins for the injector it scopes to — the library does NOT attempt to reconcile or merge across injectors. Cross-injector consistency is the consumer's responsibility.
- **`config = undefined` or `config = null`**: If a caller passes `undefined` or `null` for `config` (only reachable via `as any` since TypeScript types forbid it), `provideHtQuickNgxFire` MUST throw `HtQuickNgxFireError` with code `'invalid-config'` and the message `"FirebaseConfig is required"`. No silent default to "all simulated" — the caller's intent is unclear.
- **All required fields are empty strings**: When `firebaseOptions` is present but every required field is the empty string `""` (or whitespace-only after trim), the activation decision MUST treat each field as missing per the FR-001a "non-empty string after trimming" rule, AND the resulting `SimulationActivationError` (when `policyResolved === 'throw'`) MUST list each empty-string field by name in `error.underConfigured` so the developer can distinguish "I forgot to set it" from "the env-var substitution silently produced an empty string".
- **Simulated → real swap mid-session**: The library does NOT support hot-swapping `firebaseOptions` mid-session. Activation is a one-time decision per `provideHtQuickNgxFire` evaluation, and simulated state lives until page reload. A consumer who edits `app.config.ts` and HMR-reloads MAY end up with a real `Auth`/`Firestore` provider in the injector while simulated state from the previous bootstrap is still in memory; the simulated state MUST be considered stale and the consumer MUST reload the page to clear it. The library does NOT clear simulated state on detection of a real-mode boot.
- **Activation-decision performance**: `decideActivation` MUST be synchronous and complete in under 1ms for any well-formed `FirebaseConfig` on commodity hardware (it is a small map lookup and string-trim per service — five services). Any future change that pushes it over 1ms MUST be flagged in PR review as a regression.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: The library MUST decide simulation activation **per service**, evaluated at `provideHtQuickNgxFire` time. For each service flagged `true` in `FirebaseConfig` (auth — driven by `authOptions` having any provider enabled — plus `firestore`, `database`, `functions`, `storage`), the library MUST cross-reference the `firebaseOptions` fields that service requires to initialize. A service whose required fields are all present MUST initialize against real Firebase; a service whose required fields are missing MUST activate its simulator (in dev) or contribute to the production-mode error (in prod). Wholly missing/undefined/empty `firebaseOptions` MUST cause every enabled service to take the simulate-or-throw path.
- **FR-001a**: The per-service required-field map that FR-001 evaluates against MUST be exactly:
   - **Auth** requires `apiKey` and `authDomain`.
   - **Firestore** requires `apiKey` and `projectId`.
   - **Realtime Database** requires `apiKey` and `databaseURL`.
   - **Cloud Functions** requires `apiKey` and `projectId`.
   - **Storage** requires `apiKey` and `storageBucket`.
   A field counts as "present" only if it is a non-empty string after trimming. Because every service depends on `apiKey`, a missing `apiKey` MUST cause every enabled service to simulate (in dev) or throw (in prod). The map MUST be the single source of truth for both the activation decision (FR-001) and the production-mode error message (FR-005).
- **FR-002**: The library MUST cover every Firebase service it currently exposes — Authentication, Firestore, Realtime Database, Cloud Functions, and Cloud Storage — with a simulator that supports the full surface area of each corresponding `Ht*Service` (the consumer-facing API), so that no consumer-visible call paths through the public API throw "not supported in simulation."
- **FR-003**: When simulation mode is active, the library MUST NOT issue any network request to Firebase, Google identity providers, or any other external endpoint as part of the simulated services.
- **FR-004**: When any service activates its simulator at startup, the library MUST emit exactly one `console.warn` whose message body (a) names every service running simulated, (b) names every service running real (in hybrid configurations), and (c) names the missing `firebaseOptions` field(s) per simulated service. Testable via spying on `console.warn` and asserting `callCount === 1` per unique decision. **Dedup scope**: the dedup `Set` MUST be module-scoped (singleton across the page session, not per-injector), keyed by a stable digest of the resolved `ActivationDecision`. This means a consumer that calls `provideHtQuickNgxFire(...)` more than once in the same app (e.g., a feature module re-providing it, or two separate Angular apps in the same page) MUST get exactly one warning per *unique* decision shape: identical decisions collapse to one warning total; two decisions that differ in any per-service mode or missing-fields list each get one warning. The dedup persists for the lifetime of the page and resets on page reload.
- **FR-005**: The library MUST refuse to silently activate any service simulator in a production build under default policy. The activation decision is governed by a `simulation: 'auto' | 'force' | 'forbid'` field on `FirebaseConfig` (default `'auto'`):
   - **`'auto'`** (default): follow the framework dev/prod signal. The signal is **exactly** Angular's `isDevMode()` return value at the moment `provideHtQuickNgxFire` is evaluated — no other implicit signals (no `process.env.NODE_ENV`, no environment-file probes, no `window.location.hostname` heuristics). Missing required fields → simulate when `isDevMode() === true`; throw `HtQuickNgxFireError` when `isDevMode() === false`.
   - **`'force'`**: allow simulation regardless of build mode. Missing required fields always activate the simulator; required for test runners, Storybook, e2e harnesses, and demo deployments shipped as production builds.
   - **`'forbid'`**: never simulate. Missing required fields always throw `HtQuickNgxFireError` regardless of build mode; lets a consumer assert real-Firebase-only at runtime.
   - **Invalid value**: a `simulation` value that is not `'auto' | 'force' | 'forbid' | undefined` MUST throw `HtQuickNgxFireError` with code `'invalid-simulation-policy'` and a message naming the offending value. Silent coercion is forbidden.
   The thrown `SimulationActivationError` MUST satisfy these objectively-assertable shape rules so a test can pin it without fragile substring matching:
   - `error.code === 'simulation-activation-blocked'`.
   - `error.underConfigured` is a `Partial<Record<ServiceName, string[]>>` listing every under-configured enabled service and its specific missing `firebaseOptions` fields.
   - `error.message` MUST contain (a) every entry in `error.underConfigured` formatted as `"<service>: missing <field1>, <field2>, …"` separated by newlines, ordered by `ServiceName` declaration order (`auth, firestore, database, functions, storage`), AND (b) the exact opt-in instruction string `Set \`simulation: 'force'\` on FirebaseConfig to allow simulation in this build, or supply a complete firebaseOptions value.` as the final line. Tests MUST be able to assert both the structured `underConfigured` map and the trailing instruction string.
- **FR-006**: Setting `simulation: 'force'` on `FirebaseConfig` MUST allow simulation activation regardless of build mode. It MUST NOT, however, override the per-service required-field check in the opposite direction — if `firebaseOptions` fully satisfies a service's required fields, `'force'` does not silently swap that service to simulated. (Forcing every enabled service to simulate is achieved by simply omitting `firebaseOptions`.)
- **FR-007**: The library MUST expose a programmatic indicator describing which services are simulated and which are real (per-service map, not just a boolean), so consumers can render their own "demo mode" UI affordances and branch behavior. The indicator MUST be available before the first auth call resolves.
- **FR-008**: Simulated authentication MUST accept any sign-in attempt that the real auth service would have *attempted* (i.e., format-valid email/password, any enabled SSO provider). Sign-in MUST resolve asynchronously and produce a `User` whose shape matches what `@angular/fire` returns for the corresponding real flow.
- **FR-009**: Simulated authentication MUST be deterministic within a session — the same email or the same SSO `providerId` + simulated identifier MUST produce the same simulated `uid` until the page reloads.
- **FR-010**: Simulated Firestore MUST support all CRUD, query (`where`, `orderBy`, `limit`), transaction, batch-write, and snapshot-listener operations exposed by `HtFirestoreService`. Snapshot listeners MUST emit when data changes from any call site within the same app.
- **FR-010a**: Simulated Firestore transactions (`runTransaction`) MUST run the callback exactly once against a consistent in-memory snapshot of the document store, then commit all writes atomically. The simulator MUST NOT track per-document version numbers, MUST NOT synthesize concurrent-writer conflicts, and MUST NOT retry the callback. The first time `runTransaction` commits in a page session, the simulator MUST emit a one-time runtime warning naming this limitation and recommending the consumer validate transaction-using code against real Firestore or the Firebase Local Emulator Suite. Subsequent transaction commits in the same session MUST NOT repeat the warning.
- **FR-011**: Simulated Storage MUST support upload (with progress events), download (URL retrievable by the browser within the session), metadata read/write, and delete operations exposed by `HtStorageService`.
- **FR-012**: Simulated Realtime Database and Cloud Functions MUST support the operations consumers expect from those Firebase services. Unlike Auth/Firestore/Storage (which have `Ht*Service` wrappers), RTDB and Functions are accessed by injecting the simulator backends (`SimDatabaseBackend`, `SimFunctionsBackend`) directly — there is no `HtRealtimeDatabaseService` or `HtFunctionsService` to mediate, and consumers using real Firebase RTDB/Functions today already inject `@angular/fire/database` / `@angular/fire/functions` tokens directly. Functions calls MUST resolve to a default simulated response and MUST allow consumers to register per-callable stub responses for richer demos.
- **FR-013**: When the consumer disables a service in `FirebaseConfig` (e.g., `storage: false`), the simulator for that service MUST NOT be registered — disabled services remain absent from the injector exactly as in non-simulation mode.
- **FR-014**: All simulated state (auth session, Firestore documents, Storage blobs, RTDB trees, Functions stub registrations) MUST be ephemeral within a page session and MUST reset when the page reloads. The simulator MUST NOT write to `localStorage`, `sessionStorage`, IndexedDB, cookies, or any other persistent browser store.
- **FR-015**: The existing public API of `provideHtQuickNgxFire`, `HtAuthService`, `HtFirestoreService`, `HtStorageService`, `HtAuthAdminService`, `HtAuthUserSyncService`, and the route guards MUST NOT change in a way that breaks current consumers. `firebaseOptions` becoming optional is an additive, non-breaking change. The new exports introduced by this feature (enumerated in FR-015a) MUST all be additive — no removed exports, no narrowed types, no renamed identifiers.
- **FR-015a**: This feature MUST add **exactly** the following symbols to the library's public surface (`projects/ht-quick-ngxfire/src/public-api.ts`), and no others:
   - From `./lib/simulation/simulation.types`: `SimulationPolicy` (string literal union), `ServiceName` (string literal union), `ServiceMode` (string literal union), `ActivationDecision` (interface).
   - From `./lib/simulation/simulation-status.service`: `SimulationStatusService` (class).
   - From `./lib/simulation/auth/sim-auth.backend`: `SimAuthBackend` (class).
   - From `./lib/simulation/firestore/sim-firestore.backend`: `SimFirestoreBackend` (class).
   - From `./lib/simulation/storage/sim-storage.backend`: `SimStorageBackend` (class).
   - From `./lib/simulation/database/sim-database.backend`: `SimDatabaseBackend` (class).
   - From `./lib/simulation/functions/sim-functions.backend`: `SimFunctionsBackend` (class).
   - The `simulation?: SimulationPolicy` field added to the existing `FirebaseConfig` interface, and `firebaseOptions` becoming optional on the same interface.
   The following symbols MUST remain **internal** (not exported from `public-api.ts`): `REQUIRED_FIELDS_BY_SERVICE` (the frozen required-field map — internal because the activation decision and prod-error message are the only legitimate readers; consumers that need to inspect this should read `SimulationStatusService` instead), `decideActivation` (the pure activation function — internal because callers should not construct their own `ActivationDecision`), and the `_apply` method on `SimulationStatusService` (internal mutator used only by the provider). A characterization test (tasks.md T045b) MUST snapshot the public surface to detect accidental additions or removals.
- **FR-016**: For any service that initializes against real Firebase (whether all services or a subset in the hybrid case), the library MUST behave identically to its current behavior for that service — no new code paths, no new initialization steps, no performance regression observable to the consumer. **Tree-shake target**: in a production build with `simulation: 'forbid'` and a `firebaseOptions` value that satisfies every enabled service's required fields, the bundle MUST contain zero bytes from `projects/ht-quick-ngxfire/src/lib/simulation/auth/`, `firestore/`, `storage/`, `database/`, and `functions/` subtrees (the five `Sim*Backend` files). The activation decision logic, `SimulationStatusService`, and `SimulationActivationError` are kept (they are referenced unconditionally), but the simulator backends MUST drop out via dead-code elimination because the provider's per-service branch only references them inside the `'simulated'` arm. Verifiable by inspecting the production bundle output for any `Sim<Service>Backend` symbol — finding any of those five identifiers in a `'forbid'`+complete-config build is a regression.
- **FR-017**: `HtAuthAdminService` and `HtAuthUserSyncService` MUST work against the simulated Firestore so that role assignment, role retrieval, permission checks, and the auto-sync-on-login flow remain demonstrable end-to-end in simulation.
- **FR-018**: Route guards (`htAuthRedirectGuard`, `htRoleGuard`, `createRoleGuard`, `htAdminGuard`) MUST continue to function in simulation mode, evaluating against the simulated auth state and simulated Firestore role records. The behavior MUST be specified across all four (auth-mode × signed-in-state) combinations:
   - **real auth + signed-in real user**: existing behavior, unchanged.
   - **real auth + signed-out**: existing behavior, unchanged (`htAuthRedirectGuard` redirects to the configured login route).
   - **simulated auth + signed-in simulated user**: guards MUST evaluate the simulated `User`'s `uid` against the simulated Firestore role records and produce the same decision they would against a real `User` with the same `uid` and the same role document.
   - **simulated auth + signed-out**: guards MUST behave identically to the real-signed-out case (`htAuthRedirectGuard` redirects; role guards deny).
   In all four cases the guard MUST NOT branch on whether the underlying mode is real or simulated — the routing of `HtAuthService` / `HtFirestoreService` to a real or simulated backend is transparent to the guard's own logic.
- **FR-019**: `<ht-login>` MUST render a visible "Simulation mode" badge inside the component whenever the auth service is running simulated. Concretely:
   - **Default-on, suppressible**: rendered by default; the consumer suppresses it via a component input named `showSimulationBadge` (boolean, default `true`).
   - **Render condition**: rendered iff `SimulationStatusService.get('auth') === 'simulated'` AND `showSimulationBadge() === true`. When `auth` is `'real'` or `'disabled'` (e.g., a hybrid app with simulated Firestore but real Auth, or auth with no providers enabled), the badge MUST NOT render regardless of the input value.
   - **Position**: rendered as the first visible child of the component's root container, above the auth form, so it is in the same visual region a user looks at while signing in.
   - **Accessibility — measurable, not "AA baseline"**: the badge MUST meet WCAG 2.1 Level AA contrast — `≥ 4.5:1` between badge text and badge background (the same target FR-AUTH-14 already enforces for the rest of the component). The badge MUST be a non-interactive `<span>` (no tab stop), MUST carry `role="status"` and `aria-label="Simulation mode active"` so it is announced by screen readers without injecting a tab stop into the form's keyboard path.
   - **Styleability**: every visual property — background, foreground, padding, border-radius, font-size — MUST be exposed as a CSS custom property in the existing `--ht-login-*` token family so consumers can restyle without forking. Defaults are pinned in `tasks.md` T028.
   - **Text override / i18n**: the badge text content (the literal string `Simulation mode`) is **not** consumer-overridable in this feature — i18n / translation for the badge string is **out of scope** (see Out of Scope). Consumers needing a localized affordance MUST set `[showSimulationBadge]="false"` and render their own indicator using `SimulationStatusService` (FR-007).
   - **RTL and print**: explicit non-goals — the badge inherits whatever layout/print behavior the consumer's surrounding stylesheet establishes; the library does not ship dedicated RTL or `@media print` rules for the badge in this feature (see Out of Scope).

### Key Entities *(include if feature involves data)*

- **Simulation Activation Decision**: Inputs are (a) which services are enabled in `FirebaseConfig`, (b) which `firebaseOptions` fields are present, (c) the per-service required-field map (Auth/Firestore/RTDB/Functions/Storage each declare which `firebaseOptions` fields they need), (d) the `simulation: 'auto' | 'force' | 'forbid'` policy field on `FirebaseConfig`, and (e) under `'auto'`, the framework dev/prod signal (`isDevMode()`). Output is a per-service decision (`real` | `simulated` | `disabled`) plus a startup error if any service is under-configured and the resolved policy says "throw."
- **Simulated User**: Same shape as the real Firebase `User` returned by `@angular/fire/auth`, but produced deterministically from the email or SSO identifier within a session.
- **Simulated Document Store**: An in-memory map keyed by collection path → document id → document data, with derived indices to support `where`/`orderBy`/`limit` queries and a subscription bus to fan out snapshot events.
- **Simulated Object Store**: An in-memory map keyed by storage path → `{ blob, metadata }`, with a session-scoped URL provider so download URLs are fetchable by the browser.
- **Simulation Status**: Library-owned per-service status map (auth/firestore/database/functions/storage → `real` | `simulated` | `disabled`), exposed to consumers for "demo mode" UI and runtime branching.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: A developer with no Firebase account can install `ht-quick-ngxfire`, scaffold a minimal Angular app, render `<ht-login>`, sign in, write a document, and read it back in under 5 minutes from a clean machine — with zero external service setup.
- **SC-002**: 100% of the methods exposed by `HtAuthService`, `HtFirestoreService`, `HtStorageService`, `HtAuthAdminService`, and `HtAuthUserSyncService` execute without throwing "not supported" in simulation mode. The canonical method list is the public method set of these classes as exported from `public-api.ts` at the time of release — measurable by reflection (`Object.getOwnPropertyNames(<Service>.prototype).filter(m => m !== 'constructor' && !m.startsWith('_'))`) or by static enumeration in a spec test. A polish-phase coverage test (tasks.md T044) MUST iterate this list and assert each method either resolves or rejects (no synchronous throws) in simulation mode.
- **SC-003**: A production build under `simulation: 'auto'` (default) where any enabled service is missing required `firebaseOptions` fields fails to bootstrap with a clear, actionable error — the developer can identify which services are under-configured and which fields are missing without reading library source.
- **SC-008**: An app declaring (e.g.) `firestore: true` and `storage: true` with a `firebaseOptions` containing only `apiKey` + `storageBucket` boots cleanly in development with Storage real and Firestore simulated; the per-service status map (FR-007) reports exactly that split; the startup warning (FR-004) names both states. Verified automatically — the integration test in tasks.md T044 includes a hybrid-config case that asserts `status.get('firestore') === 'simulated'`, `status.get('storage') === 'real'`, and that the `console.warn` body contains both service names with correct mode labels. Manual smoke validation in T030 corroborates end-to-end.
- **SC-004**: Existing consumers who supply a real `firebaseOptions` see zero behavioral changes and zero new console output after upgrading to the version that introduces simulation mode.
- **SC-005**: The full pre-existing test suite (`ng test ht-quick-ngxfire`) passes with no modifications, and the library still builds with `ng build ht-quick-ngxfire` with zero errors.

Verified by spying on `window.fetch` and `XMLHttpRequest.prototype.open` in tasks.md T044 and asserting `fetch.calls.count() === 0` AND `XMLHttpRequest.prototype.open.calls.count() === 0` after running a representative simulator workflow (sign-in, write+read, upload+download, push+listen, callable). ## Assumptions

- "Defaults to that for all the firebase services" is interpreted as: every Firebase service the library currently exposes (Auth, Firestore, RTDB, Functions, Storage) gets a simulator. Nothing outside the library's current surface area (e.g., Analytics, Performance, Messaging) is added in this feature.
- The simulation policy field on `FirebaseConfig` is `simulation: 'auto' | 'force' | 'forbid'` with default `'auto'`. The exact TypeScript shape (string literal vs enum vs symbol) is a `/speckit.plan` decision, but the three resolved behaviors are spec-frozen.
- "No firebase config json" is interpreted at two levels: (a) wholly missing/`undefined`/empty `firebaseOptions` causes every enabled service to take the simulate-or-throw path; (b) partially-supplied `firebaseOptions` is evaluated per-service against the FR-001a required-field map, allowing hybrid real+simulated apps. The all-or-nothing reading from earlier drafts has been replaced by per-service evaluation.
- Simulated state is ephemeral (in-memory, page-session-scoped). Persisting simulated data across reloads (e.g., to `localStorage`) is out of scope for this feature; it can be revisited later if developer feedback asks for it.
- Production-mode detection in `simulation: 'auto'` uses the Angular runtime's existing dev/prod signal (`isDevMode()`); no new build-time configuration is introduced. Consumers who need to override per-environment use `'force'` or `'forbid'` rather than a custom dev-mode probe. **Assumption**: the consumer's app calls `enableProdMode()` (if at all) **before** any provider is evaluated — typically before `bootstrapApplication`. Calling `enableProdMode()` after `provideHtQuickNgxFire` has been evaluated does NOT retroactively flip the activation decision; the decision is captured once at provider time and stored in `SimulationStatusService` for the page session's lifetime.
- Simulated data is not seeded with any default documents, users, or files — every simulator starts empty. Consumers can populate state through the normal service APIs in their app's bootstrap if they want a richer demo.
- Cloud Functions simulation returns a configurable default response (e.g., `null` or an empty object) per callable, with an opt-in registration API for consumers who want richer behavior in a demo. The default response shape is a `/speckit.plan` decision.

## Dependencies

- This feature lives entirely inside the existing `ht-quick-ngxfire` library — no new packages, no new workspace projects.
- The simulation implementation MUST coexist with `@angular/fire` ^21.0.0 (currently resolved to the workspace's `next` tag, `21.0.0-rc.0`) without forcing a downgrade or upgrade of that peer dependency. **Failure mode for incompatible versions**: if a consumer ships against `@angular/fire` < 21 or a future major (22+), the library makes no compatibility guarantees — the activation decision and `SimulationStatusService` will still work, but the constructor-branch real-path tokens (`Auth`, `Firestore`, `Storage`) may differ in shape. The `peerDependencies` range in `package.json` (`@angular/fire`-using libraries) is the single source of truth for supported versions; npm's standard peer-mismatch warning is the supported failure surface.
- This feature must land **after** the in-flight `001-quick-ngxfire` work (the AuthUI → custom-component refactor) is complete on `main`, because the simulator hooks into `HtAuthService` and `HtLoginComponent` as defined by that feature.
- This feature depends on Angular's `isDevMode()` returning the framework's authoritative dev/prod signal at the moment `provideHtQuickNgxFire` is evaluated. Consumers MUST NOT call `enableProdMode()` after the provider has been evaluated and expect that to retroactively change the activation decision (it won't — the decision is captured once and stored in `SimulationStatusService`).

## Out of Scope

- Persisting simulated state across page reloads (localStorage, IndexedDB).
- A UI inspector or developer panel for browsing simulated state at runtime.
- Seeded fixtures or a fixture-loading API for the simulator.
- Network-level emulation that would also intercept consumer-written `fetch`/`XMLHttpRequest` calls outside the library.
- Optimistic-concurrency contention emulation in simulated Firestore transactions (per FR-010a — single-pass atomic commit with documented limitation; consumers needing contention-aware testing must use real Firestore or the Firebase Local Emulator Suite).
- Compatibility with the official Firebase Local Emulator Suite (`firebase emulators:start`). Consumers who want emulator parity should keep providing `firebaseOptions` pointing at the emulator host.
- Multi-tenant or multi-app simulation (more than one simulated Firebase app in the same Angular app).
- Simulation of Firebase services not currently exposed by `ht-quick-ngxfire` (Analytics, Performance, Messaging, App Check, Remote Config).
- **i18n / translation of the simulation badge string** (FR-019). The string `Simulation mode` is hard-coded; consumers needing a localized affordance set `[showSimulationBadge]="false"` and render their own indicator using `SimulationStatusService` (FR-007). Adding a translatable token can be revisited if developer feedback asks.
- **RTL (right-to-left) layout support specifically for the badge**. The badge inherits whatever `direction` / writing-mode the consumer's surrounding stylesheet establishes. The library does NOT ship dedicated `[dir="rtl"]` rules for the badge in this feature.
- **Print stylesheet behavior for the badge** (`@media print`). The library does NOT ship a `@media print` rule for the badge. Consumers who care about printing demo screens MUST add their own rule (the badge is selectable via `.ht-login__sim-badge`).
- **Hot-swapping `firebaseOptions` mid-session**. Activation is decided once per `provideHtQuickNgxFire` call; switching between real and simulated mode during a running session is not supported (consumer must reload the page).
